## 연결 사례의 남은 문제와 v2.1 수정

H02 RCA는 과거 dbt_orders 접속 거부, 현재 probe 성공이 복구 증명이 아니라는 점, 명시적으로 기록된 run_results 누락을 올바르게 설명했다. 조치는 먼저 실제 엔드포인트와 설정을 확인하고 '확인된 설정 문제만' 사람이 수정하도록 제안했다. Reviewer는 이를 이미 설정 문제가 확인됐다는 전제로 해석해 거절했고, 최종 결과는 안전하게 UNKNOWN/insufficient와 조치 없음으로 끝났다. 후보와 검토 피드백은 `artifacts/revision-v2/H02-final.json`의 `rejected_candidates`에 남아 있다.

이 판단에는 조건문을 더 명확히 쓸 여지가 있고, Reviewer가 조건부 점검을 과도하게 거절한 것으로도 해석된다. 독립 사람 평가로 확정한 결론은 아니다. v2.1은 **설정 오류가 확인된 경우에만 수정하고, 확인되지 않으면 변경하지 않는다**는 조건을 RCA에 추가했다. Reviewer에는 역사적 연결 거부의 확인과 현재 설정 오류의 확인을 구분하도록 명시했다. 유료 첫 결과와 v2 코드는 수정하지 않았다. 이 프롬프트 변경의 실제 모델 효과는 미검증이다.

## 비교 입력과 해시

두 방식은 각 사례에서 다섯 관측의 전체 내용을 독립적으로 받았다. baseline에 v2 수집 실패 시의 일부 입력만 주던 문제는 제거했다. 실제 JSON의 관측 배열 순서는 달랐다. 그래서 최초 실행기의 순서에 민감한 `same_full_evidence`는 false다. 최초 결과를 고치지 않고 `paired-content-audit.json`에서 ID 기준 정렬 후 모든 관측의 값과 해시가 같음을 확인했다. 같은 내용의 증거라는 뜻이며 완전히 같은 바이트나 프롬프트라는 뜻은 아니다. v2.1 baseline은 향후 비교를 위해 도구 순서도 맞추도록 정리했으며, 이미 실행한 두 사례에는 소급 적용하지 않았다.

평가용 Inspector에는 나머지 네 도구 전체 수집을 지시했다. 실제 제품의 선택적 도구 수집과 구분한다. 같은 모델·Flex·reasoning none·RCA 출력 상한을 사용했지만, 네 역할·검색·검토를 함께 비교하므로 특정 기술 하나의 효과를 분리하지 않는다.

이 두 사례에서는 v2가 더 느리고 비용도 많았으며 정확도 우위는 확인되지 않았다. 유료 추가 호출은 여기서 종료했다. v2.1은 추가 유료 호출 0회다.

## 비용·보안·보존

같은 로컬 장부 누적은 **93회, $0.015592371**, 불확실 예약 0건이다. 기존 상한 하루 $0.02·누적 $0.05·진단 $0.01·요청 보수 추정 $0.005·진단 최대 4회와 evaluation 요청 수 제한을 유지했다. 일반 유료 경로는 기존 요청 수 상한을 이미 넘었으므로 새 네트워크 호출 전에 차단된다. 이 집계는 해당 장부의 API 사용량과 단가 기반 추정이며 계정 청구서나 공용 키 전체 지출은 아니다.

키는 기존 명시적 설정 파일 밖으로 복사하지 않았다. 배포 ZIP에서 키·장부·응답 캐시·가상환경·모델 가중치를 제외한다. 원문 오류를 수리하거나 재시도하지 않았으며 다른 모델이나 일반 요금으로 전환하지 않았다. v1과 기존 ZIP, v2 최초 평가 코드 및 출력은 보존했다. 이번에는 실제 파이프라인 장애를 재주입하지 않았다. v1의 실제 복구 3/3은 과거 결과로 남긴다.

다음 평가 전에는 독립 사람 검토표로 H02 거절의 적절성을 확인하고, v2.1을 포함한 새 개발 세트를 충분히 점검해야 한다. 이후 별도 새 최종셋과 예산 계획으로 정확도 목표를 재평가해야 한다. 이 단계는 아직 완료되지 않았다. 발표자료는 만들지 않았다.
