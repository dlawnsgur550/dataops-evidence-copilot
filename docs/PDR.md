## 목적과 완료 목표

데이터 엔지니어가 실패 로그, DB 스키마, dbt 검사 결과, 대응 문서를 따로 확인해야 하는 과정을 하나의 진단 흐름으로 연결한다. 서비스 지연을 분석하는 일반 운영 Agent와 달리 스키마 변화, 데이터 품질, dbt 모델 의존관계를 다룬다.

첫 버전의 완료 목표는 다음과 같다.

- 실제 Airflow와 PostgreSQL에서 정상 실행과 장애 3종을 재현한다.
- MCP 프로토콜을 통해 실제 상태와 로그를 조회한다.
- 역할별 에이전트가 원인, 근거, 영향 범위, 복구안을 생성한다.
- 복구안을 사람이 적용한 뒤 파이프라인과 품질 검사의 성공을 확인한다.
- 고정된 평가 사례로 기본 버전과 최종 버전의 정확도, 시간, 호출량을 비교한다.

성능 목표는 개발 합격 기준이며 측정 결과가 아니다. 기술을 설치한 것과 기능이 실제로 동작하는 것을 구분한다.

## 사용자와 사용 흐름

주 사용자는 로컬 데이터 파이프라인을 관리하는 데이터 엔지니어다. 평가자는 재현 절차, 코드, 진단 근거와 측정 결과를 확인한다.

1. 개발자가 정상 또는 장애 시나리오로 데모 DAG를 실행한다.
2. 사용자가 화면에서 DAG, 실행, 태스크를 선택해 진단을 요청한다.
3. 시스템이 증거를 수집하고 런북을 검색해 진단 보고서를 만든다.
4. 사용자가 보고서의 근거와 복구 조건을 확인한다.
5. 개발자가 코드나 설정 또는 데이터를 수정하고 다시 실행한다.
6. 사용자가 새 실행을 선택해 성공 상태와 품질 검사 결과를 확인한다.

첫 버전은 요청 버튼으로 시작한다. 자동 감지 주기나 스트리밍 처리 지연에 관한 서비스 수준은 약속하지 않는다.

## 데모 파이프라인과 장애 시나리오

정상 파이프라인은 다음 작업을 수행한다.

```text
load_demo_data → dbt_run → dbt_test → publish_summary
```

원본 주문 테이블에는 order_id, customer_id, amount, created_at을 둔다. 정상 데이터는 고정 시드로 생성한 약 1,000건을 사용한다. 원본에는 품질 오류를 적재할 수 있도록 order_id에 NOT NULL 또는 기본키 제약을 걸지 않고, dbt에서 not_null과 unique를 검사한다. 모델은 stg_orders와 daily_orders를 둔다.

| 사례 | 주입 방법 | 관측되는 증상 | 기대 진단과 조치 |
| --- | --- | --- | --- |
| SCHEMA_CHANGE | 적재 단계에서 amount 대신 paid_amount를 생성 | dbt_run에서 참조 컬럼 오류 | 실제 컬럼 차이와 참조 모델을 제시하고 스키마 계약 또는 SQL 수정 안내 |
| DATA_QUALITY | 원본 order_id에 NULL 삽입 | dbt_run 이후 dbt_test의 not_null 실패 | 실패 검사, NULL 수와 제한된 샘플을 제시하고 수정 또는 격리 후 재검사 안내 |
| CONNECTION_FAILURE | dbt 전용 연결의 포트를 잘못 지정 | dbt_run 연결 실패 | 태스크 연결 실패를 확인하고 설정 확인과 정상화 후 재실행 안내 |
| NORMAL | 정상 데이터와 연결 사용 | 모든 태스크와 검사 성공 | 정상 상태를 표시하고 복구 조치를 생성하지 않음 |
| INSUFFICIENT_EVIDENCE | 오류 내용 또는 필수 조회 결과 누락 | 원인 확정에 필요한 증거 부족 | 판단 보류와 추가 확인 사항 반환 |

스키마 오류는 적재가 끝난 뒤 모델 생성 전에 유효해야 한다. 초기화 작업이 주입한 장애를 지우지 않도록 시나리오별 데이터 준비를 분리한다. 연결 실패는 dbt용 연결만 변경해 재현하며, Airflow 메타데이터 DB나 MCP용 조회 연결의 장애와 혼동하지 않는다. 로그만으로 잘못된 포트가 확정되지 않으면 연결 실패까지만 진단한다.

각 사례의 실행 전에 데모 스키마와 설정을 초기화한다. 초기화는 개발자 스크립트의 책임이며 MCP 조회 계정에는 해당 권한을 주지 않는다. scenario_id, 정답 라벨, 주입 함수 이름은 에이전트 입력과 평가용 증거에서 제외한다.

## MCP 도구 계약

첫 버전은 FastMCP 기반의 로컬 stdio 서버 하나를 사용한다. MCP Inspector와 실제 클라이언트로 initialize, tools/list, tools/call을 확인한다. 직접 함수 호출만 통과한 결과를 MCP 연동 성공으로 처리하지 않는다.

| 도구 | 필수 인자 | 반환 내용 |
| --- | --- | --- |
| get_task_context | dag_id, run_id, task_id, try_number | 태스크 상태, 시각, 시도 횟수, 제한된 로그, dbt 작업 연결 정보 |
| compare_schema | 허용된 table_id, baseline_id | 현재 스키마, 정상 스냅샷, 추가·삭제·타입 변화, 스냅샷 수집 시각 |
| get_quality_profile | table_id, 허용된 column_ids | 전체 데모 테이블의 건수·NULL·중복 통계와 최대 5개 오류 샘플 |
| get_dbt_artifacts | dag_id, run_id, task_id, try_number | 해당 dbt 호출의 manifest, run_results, 관련 노드와 의존관계 |
| check_connection | 허용된 connection_id | 해당 조회 연결의 접속 성공 여부, 제한된 대상 정보, 오류 유형 |

check_connection의 성공은 검사한 연결에만 적용된다. MCP 조회 계정이 정상 연결됐다는 사실만으로 실패한 dbt 프로세스의 설정이 정상이라고 결론내리지 않는다.

공통 반환에는 status, data, evidence_id, source, observed_at, target_ref, error를 둔다. status는 success, empty, unavailable, invalid_input으로 구분한다. error에는 code, retryable, message를 기록한다. 대상이 없는 조회와 네트워크 오류를 구분한다.

도구 설명에는 용도, 입력 제약, 반환 범위와 오류 의미를 적는다. 테이블·컬럼·경로는 허용 목록으로 제한하고 SQL은 사전에 정의한 조회만 실행한다. 자격증명, 토큰, DB 비밀번호는 반환하지 않는다. readOnlyHint는 설명용 힌트이며 DB 권한과 입력 검사를 대체하지 않는다.

런북 원문은 Resource로 제공할 수 있으나 RAG 구현의 필수 조건은 아니다. 실제 진단 지시문은 파일로 버전 관리하며 MCP Prompt를 추가하더라도 동일한 정의를 사용한다.

## 증거와 진단 자료 구조

자료 구조는 Pydantic으로 검증한다. 아래는 구현할 필드 계약이며 실행 결과 예시는 아니다.

| 자료 구조 | 핵심 필드 | 제약 |
| --- | --- | --- |
| IncidentRef | incident_id, dag_id, run_id, task_id, try_number | 재시도와 다른 실행을 구분 |
| EvidenceItem | evidence_id, kind, source, observed_at, target_ref, payload, status | 현재 DB 조회와 과거 실행 로그의 관측 시점을 구분 |
| RetrievalHit | doc_id, doc_version, chunk_id, rank, content_hash, content | 문서와 청크를 추적하고 평가셋 정답은 포함하지 않음 |
| Diagnosis | category, diagnosis_status, severity, cause, evidence_ids, missing_evidence, impact | 원인 주장마다 존재하는 evidence_id를 연결 |
| RecoveryAction | action_id, target_ref, prerequisites, steps, verification, evidence_ids | 실행 명령은 검토 가능한 텍스트이며 자동 실행하지 않음 |
| ReviewResult | accepted, violations, feedback, revision_count | accepted는 정해진 검토 통과이며 복구 성공과 다름 |
| RecoveryCheck | original_incident_id, followup_run_id, task_statuses, quality_results, recovered | 사람이 수정한 후속 실행으로 판정 |

category는 SCHEMA_CHANGE, DATA_QUALITY, CONNECTION_FAILURE, NORMAL, UNKNOWN 중 하나다. diagnosis_status는 supported, insufficient, failed로 구분한다. INSUFFICIENT_EVIDENCE 사례의 기대 결과는 category=UNKNOWN, diagnosis_status=insufficient이다. severity는 high, medium, low, unknown이며 수치형 확률을 생성하지 않는다.

심각도는 데모에서 사전에 정한 규칙으로 산정한다. publish_summary를 차단하는 장애는 high, 공개 집계를 차단하지 않는 개별 검사 실패는 medium, 정상은 low, 영향 정보가 없으면 unknown이다. 실제 운영 중요도를 추정한 값으로 설명하지 않는다.

dbt 산출물은 실행, 태스크, 시도, 명령 호출별로 보존한다. manifest는 정의와 의존관계에, run_results는 해당 호출의 상태와 메시지에 사용한다. 현재 스키마를 과거 실행의 스키마로 간주하지 않고 정상 기준 스냅샷과 비교한다.

## RAG와 에이전트 동작

초기 지식은 직접 작성한 런북 9개와 합성 장애 기록 3개로 구성한다. 관련 문서 외에 비슷한 증상의 다른 원인과 적용 불가 사례를 넣는다. 문서에는 증상, 원인, 확인 절차, 조치, 선행 조건, 검증 방법, 적용 제외 조건, 수정일을 적는다. 평가 로그나 사례별 정답 보고서를 검색 문서로 넣지 않는다.

제목과 절차를 보존해 청킹하고 multilingual-e5-small의 토크나이저 기준 최대 350토큰, 겹침 최대 50토큰을 초기값으로 사용한다. 제목과 query 또는 passage 접두사를 포함한 최종 입력이 모델 한도를 넘지 않도록 검사한다. 임베딩 모델과 revision, 청킹 설정, 원문 해시를 인덱스 메타데이터에 저장한다.

BM25와 Dense에서 각각 상위 10개 청크를 가져온다. 순위 기반 RRF는 k=60을 사용한다. 같은 문서는 최고 청크 순위를 기준으로 묶어 서로 다른 문서 상위 3개와 대표 청크를 제공한다. BM25 점수와 벡터 유사도를 직접 더하지 않는다. 이 초기값은 개발셋에서만 조정한다.

| 역할 | 책임과 도구 | 출력 |
| --- | --- | --- |
| Triage | 선택된 상태와 최소 로그로 잠정 분류, 조사 항목 제안 | 잠정 유형, 필요한 증거, 조사 계획 |
| Inspector | 계획과 허용 도구에 따라 MCP 조회, 증거 정리 | 증거 목록, 실패와 누락, 실제 수행한 조회 |
| RCA | 증거에서 검색 질의를 만들고 런북과 현재 상태 대조 | 원인 후보, 연결 근거, 영향 가능성, 복구안 |
| Reviewer | 보고서와 증거를 검토하고 코드 검사 결과 반영 | 통과, 추가 조사, 재작성, 판단 보류 |

공유 State에는 incident_ref, plan, evidence, retrieval_hits, diagnosis, review, errors, usage, replan_count, revision_count를 둔다. 조사 추가와 보고서 재작성은 각각 최대 1회이며 전체 호출 예산 안에서만 수행한다.

Reviewer의 의미 검토와 별도로 코드가 대상 허용 여부, 필드 누락, 근거 ID 존재, 금지된 실행 종류, 반복 상한을 검사한다. 스키마·품질 오류에 재시도만 제안하면 통과시키지 않는다. 원인에 필요한 증거를 얻지 못하면 원인과 복구를 확정하지 않는다.

## 테스트와 평가

| 종류 | 검증 대상 | 통과 조건 |
| --- | --- | --- |
| UT | 로그·dbt 파서, 스키마 차이, 품질 통계, 자료 구조 | 정상, 누락, 잘못된 입력, 조회 실패 사례를 각각 검사 |
| IT | MCP 세션·목록·호출, Airflow 인증, DB·산출물 조회 | 실제 읽기 계정과 실제 프로토콜을 사용한 증거 확보 |
| E2E | 스키마, NULL, 연결 실패 | 각 사례에서 실패 → 진단 → 사람 조치 → 새 실행 성공과 품질 검사 통과 |
| NEG | 근거 ID 조작, 대상 누락, 재시도만 제안, 누락 로그, 다른 연결의 성공 오용, 과거 산출물 혼입 | 부적절한 확정·조치를 차단하거나 부족한 근거를 명시 |
| EV | 기본 버전과 최종 버전 | 동일한 고정 증거, 평가 문서 버전, 모델·설정으로 비교 |

개발셋은 6건, 최종 평가셋은 12건이다. 최종 평가셋은 장애 3종 각 3건, 정상 1건, 근거 부족 2건으로 고정한다. 단순 문구 치환만으로 사례를 늘리지 않고 테이블·태스크, 로그 위치, 오류 표현과 누락 상태를 바꾼다. 프롬프트·검색 설정 확정 뒤 평가셋을 사용하고, 평가를 보고 수정하면 새 버전의 재평가로 표시한다.

기준 버전은 단일 LLM이 고정된 증거를 읽는 방식이다. 최종 버전은 같은 증거에 RAG와 역할별 검토를 적용한다. MCP 수집 정확도는 IT와 E2E에서 별도로 확인한다. 여러 기능의 효과를 묶어 비교하므로 Multi-Agent 단독의 개선 효과로 해석하지 않는다.

| 지표 | 계산과 분모 | 완료 목표 |
| --- | --- | --- |
| 원인 진단 | 장애 9건의 유형, 사례별 원인 요소, 필수 근거 충족을 고정 채점표로 판정 | 8건 이상 정답 |
| 검색 Hit@3 | 검색 대상 장애 9건 중 허용된 정답 문서 ID가 상위 3개 문서에 존재 | 8건 이상 적중 |
| 정상·보류 대응 | 정상 1건, 근거 부족 2건 | 세 건 모두 불필요한 조치나 원인 확정 방지 |
| 검토 규칙 | NEG에 정의한 여섯 오류 유형 | 모든 유형 검출 |
| 실제 복구 | E2E의 세 장애 | 세 건 모두 새 실행과 품질 검사 성공 |
| 시간과 사용량 | 진단별 전체 시간, 단계별 시간, LLM·도구 호출, 토큰 | 모든 평가 실행 기록, 평균·최댓값과 개별 실패 제시 |

LLM 기반 Faithfulness와 관련성 평가는 보조 지표다. 도구 모킹 성공, 문맥 충실성, 실제 장애 진단 정답과 실제 복구 성공을 각각 구분해 보고한다. 작은 합성 평가셋의 결과를 운영 환경 전체의 정확도로 일반화하지 않는다.

## 모듈과 구현할 실행 인터페이스

아래 경로는 향후 구현할 저장소 구조다. 현재 문서 배포에 해당 코드가 포함돼 있다는 의미는 아니다.

```text
pipeline/          Airflow DAG와 dbt 프로젝트
extractors/        Airflow API와 PostgreSQL 및 dbt 산출물 파서
mcp_server/        조회 도구와 로컬 서버 진입점
rag/               청킹과 임베딩 및 BM25 Dense RRF
agents/            역할별 지시문과 도구 정책
workflow/          LangGraph 상태와 실행 제어
schemas/           Pydantic 자료 구조
ui/                Streamlit 화면
runbooks/          직접 작성한 대응 문서
tests/             단위 통합 부정 사례 검사
evaluation/        고정 증거와 비공개 정답 및 결과 집계
scripts/           환경 점검 실행 초기화 평가
artifacts/         실행별 산출물과 진단 보고서
docs/              PDR와 ADR 및 운영 설명
```

개발자는 setup, start, reset_demo, run_scenario, build_index, diagnose, evaluate에 해당하는 실행 진입점을 구현하고 README에 실제 명령을 적는다. diagnose는 조회와 보고만 수행하고 run_scenario와 reset_demo는 개발자용으로 분리한다. 각 단계의 검증 기록에는 실행 명령, 종료 코드, 실행 ID, 생성 파일, 실패 및 미확인 범위를 남긴다.

환경 설정은 LLM 제공자·모델, Airflow API 주소·인증, 읽기 DB 연결, 아티팩트 경로, 인덱스 경로를 명시한다. 모델과 자격증명은 실제로 사용 가능한 값을 구현 시작 시 확정한다. 비밀값 없는 .env.example과 검증된 의존성 목록을 제공하고 실제 비밀값은 Git에 넣지 않는다.

- [ ] 정상 상태와 근거 부족 상태를 별도로 처리한다.

- [ ] 제출 링크의 접근 권한을 확인하고 사람이 등록한다.

이 체크리스트는 개발 완료 확인용이다. 문서 작성 시점에는 체크하지 않는다.

## 한계와 후속 확장

첫 버전은 하나의 합성 배치 파이프라인과 제한된 장애 유형에 맞춘다. 현재 DB 관측과 과거 태스크 실행 사이에 시간 차이가 있을 수 있으며, 상태가 바뀌면 추가 확인이 필요하다. 런북이 오래됐거나 검색이 빗나가면 답변도 잘못될 수 있다. 추가 에이전트와 검토는 지연·호출량을 늘린다. 검토 통과는 운영 안전성이나 복구 성공의 보증이 아니다.

후속 확장은 Kafka 장애 수집, Prometheus 기반 감지, FastAPI와 SSE, 영속 Checkpointer, 제한된 승인 후 실행 도구 순서로 별도 ADR을 작성해 검토한다. 에이전트의 쓰기 권한을 추가하는 변경은 현재 조회 전용 계약을 대체하는 새 설계를 필요로 한다.
