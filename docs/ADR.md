## ADR 0001 로컬 배치 장애 진단과 사람에 의한 복구

상태: 채택(C의 실제 로컬 데모 범위, 2026-10-20). 실제 장애 3종과 개발자 조치 후 새 실행·품질·집계 검증을 통과했다. 사람이 직접 편집한 시연은 아니며 승인된 개발자 스크립트가 조치했다. 관련 요구사항: FR-01, FR-02, FR-09, FR-12.

### 배경

3일 안에 실제 동작과 평가를 설명해야 한다. 배치·스트리밍·다중 DW·자동 복구를 동시에 구현하면 연결 설정과 실행 권한 처리에 시간이 많이 든다. 첫 버전은 데이터 품질과 스키마 변화를 원인 증거로 제시하는 데 집중한다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| 배치와 스트리밍 통합 및 자동 복구 | 넓은 기능 범위 | Kafka 장애 모델, 오프셋, 쓰기 권한, 중복 실행 검증까지 필요 |
| 로컬 배치 진단과 수동 조치 | 장애 재현과 복구 확인을 반복하기 쉬움 | 자동 처리와 스트리밍 대응은 제공하지 못함 |
| 로그 파일만 사용하는 모의 진단 | 빠른 개발 | 실제 도구 연동과 상태 확인을 입증하기 어려움 |

### 선택안

실제 로컬 배치 파이프라인 하나, 장애 세 종류, 조회 전용 에이전트로 시작한다. 복구안은 사람이 적용한다. 시스템은 별도의 후속 실행을 조회해 태스크와 데이터 품질이 모두 성공했는지 확인한다. 요청 버튼으로 진단을 시작한다.

자동 실행 도구와 승인 UI는 첫 버전의 필수 구현에 넣지 않는다. 예시 명령을 생성하더라도 실행 권한을 부여하지 않는다.

### 영향

실제 상태 수집과 근거의 정확성을 우선 검증할 수 있다. 반면 자동 복구율, 무인 운영, 스트리밍 지연 목표는 주장할 수 없다. 사람의 수정 시간은 에이전트 진단 지연과 분리해 기록해야 한다.

### 검증 조건

- 실제 장애 세 종류의 실패 태스크를 확인한다.
- 진단 보고서에서 원인과 증거, 선행 조치, 성공 확인 방법을 연결한다.
- 사람이 수정한 후속 실행에서 전체 태스크와 품질 검사 성공을 확인한다.
- 에이전트의 도구 목록에 DB 쓰기, DAG 실행, 셸 실행이 없다.

### 재검토 조건

Kafka 소비 지연이나 스키마 레지스트리 문제를 추가하거나, 운영 대상에 대한 실행 권한이 필요해질 때 새 ADR로 범위와 통제 방식을 설계한다.

## ADR 0002 Airflow와 PostgreSQL 및 dbt 실행 환경 분리

상태: 원안 대체(C-0011, 2026-10-20). 환경 분리 원칙을 유지하되 macOS Gunicorn SIGSEGV 때문에 Airflow 실행 구성을 공식 Linux 컨테이너로 바꿨다. 관련 요구사항: FR-01, FR-02, NFR-01.

### 배경

Airflow와 dbt, 에이전트 라이브러리는 서로 다른 의존성 요구를 가질 수 있다. 하나의 Python 환경에 모두 설치하면 원인 파악이 어려운 충돌이 생길 수 있다. 장애 주입 시 Airflow 제어 기능까지 중단되면 실패 로그 수집이 어려워진다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| 모든 패키지를 하나의 환경에 설치 | 초기 구성 단순 | 의존성 충돌과 장애 범위 확대 |
| Airflow 공식 전체 분산 구성 | 확장성 있는 환경 학습 | 1인 로컬 데모에 불필요한 프로세스와 자원 사용 |
| standalone과 실행 환경 분리 | 적은 서비스로 실제 실행 가능 | 개발용 구성의 한계를 설명해야 함 |

### 선택안

Airflow는 constraints를 적용한 전용 환경의 standalone으로 운영한다. PostgreSQL은 별도 로컬 컨테이너로 실행한다. dbt Core와 dbt-postgres는 전용 가상환경에 설치하고 Airflow 태스크는 그 실행 파일의 절대 경로로 호출한다. 에이전트·UI·MCP 관련 패키지는 별도 앱 환경으로 관리한다.

Airflow 메타데이터는 standalone이 지원하는 개발용 저장 구성을 사용하고, 업무 데이터의 PostgreSQL과 구분한다. dbt 연결 실패 주입은 dbt용 설정에만 적용한다. Airflow API에는 고정한 버전에 맞는 인증을 구현한다.

정확한 버전은 설치 성공, 정상 DAG, API 조회를 확인한 조합으로 고정한다. constraints, 패키지 lock, 이미지 태그 또는 digest, Python 버전을 남긴다. 최신 문서의 샘플을 버전 확인 없이 혼합하지 않는다.

### 영향

의존성과 장애 범위를 분리할 수 있고 원본 데이터 DB를 통제하기 쉽다. 환경이 여러 개라 실행 경로와 설정 문서가 필요하다. standalone은 개발 데모 구성으로 설명하며 운영 적합성을 주장하지 않는다.

### 검증 조건

- 새 환경에서 정상 DAG와 dbt 검사가 성공한다.
- Airflow API 인증 후 선택한 실행의 상태와 로그를 조회한다.
- dbt 포트 오류를 주입해도 Airflow API와 기존 로그 조회가 가능하다.
- 업무 DB, Airflow 메타데이터, 앱 실행 환경의 위치와 버전을 README에 기록한다.

### 재검토 조건

다중 개발자, 원격 실행, 장기 운영, 운영용 메타데이터 저장 또는 컨테이너 일괄 배포가 필요할 때 실행 환경을 다시 설계한다.

공식 근거: [Airflow Quick Start](https://airflow.apache.org/docs/apache-airflow/stable/start.html), [Airflow Public API](https://airflow.apache.org/docs/apache-airflow/stable/security/api.html).

## ADR 0003 조회 전용 MCP 서버와 로컬 stdio 연결

상태: 제안. 관련 요구사항: FR-03, FR-04, NFR-02.

### 배경

Airflow, DB, dbt 산출물 조회에 공통 도구 계약이 필요하다. 직접 API 함수만 호출하면 구현은 간단하지만 MCP 기술의 실제 사용을 입증할 수 없다. 한편 서버를 여러 개로 나누면 초기 연결·인증·수명 관리가 복잡해진다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| Python 함수 직접 호출 | 가장 단순 | MCP 연동 검증을 대체하지 못함 |
| 단일 로컬 MCP 서버와 stdio | 실제 프로토콜과 프로세스 경계, 네트워크 서버 관리 감소 | 단일 호스트와 프로세스 관리에 한정 |
| 시스템별 원격 MCP 서버 | 독립 배포와 공유 | 다중 서비스, 인증·네트워크 운영 필요 |

### 선택안

독립 배포되는 fastmcp 패키지로 서버 하나를 만든다. 앱이 서버를 자식 프로세스로 실행하고 stdio로 연결한다. 공식 MCP SDK에 포함된 과거 FastMCP 구현과 별도 fastmcp 패키지를 같은 것으로 가정하지 않는다. 선택한 안정 버전과 LangChain MCP 어댑터의 연동을 먼저 확인한다.

앱의 명시적 연결 컨텍스트가 MCP 세션을 소유한다. 연결 동안 초기화와 도구 로드를 한 번 수행하고, 종료·연결 오류 때 컨텍스트를 닫아 자식 프로세스를 정리한다. 어댑터 객체를 재사용했다는 이유만으로 세션이나 subprocess도 재사용된다고 간주하지 않는다. SDK가 제공하는 명시적 세션 동작과 프로세스 시작 횟수를 검사한다.

도구는 PDR의 다섯 가지 조회만 노출한다. DB 읽기 권한, 허용 대상·경로와 입력 검사를 서버에서 강제한다. 표준 출력은 프로토콜에 사용하고 서버 로그는 표준 오류로 보낸다. Tool은 호출 기능, Resource는 식별 가능한 런북 원문, Prompt는 재사용할 지시문 템플릿으로 구분한다. Resource가 항상 불변이어야 한다고 가정하지 않는다.

### 영향

도구 경계를 통일하고 Inspector와 클라이언트로 검사할 수 있다. 프로세스·세션의 정상 종료와 오류 전파를 구현해야 한다. MCP 표준화와 readOnlyHint 자체가 DB 권한을 보장하지 않으므로 실제 권한 검증이 필요하다.

### 검증 조건

- initialize, tools/list, tools/call이 실제 클라이언트에서 성공한다.
- 호출이 Airflow 또는 DB의 실제 결과에 도달했음을 실행 ID와 응답으로 확인한다.
- 연속 두 진단에서 연결 정책에 맞는 프로세스 수와 재연결 횟수를 확인한다.
- 잘못된 대상, 경로 이탈, 임의 SQL 입력을 거부하고 쓰기 권한이 없음을 확인한다.
- MCP Inspector로 입력 스키마, 오류 반환, 출력 계약을 확인한다.

### 재검토 조건

여러 앱이 서버를 공유하거나 원격 실행이 필요해지면 Streamable HTTP와 인증·접근 제어를 별도 ADR로 검토한다. FastAPI를 채택한다면 연결 수명은 lifespan에 연결한다.

공식 근거: [FastMCP](https://gofastmcp.com/getting-started/welcome), [LangChain MCP](https://docs.langchain.com/oss/python/langchain/mcp), [MCP 서버 개념](https://modelcontextprotocol.io/docs/learn/server-concepts).

## ADR 0004 LangGraph와 역할별 에이전트 및 명시적 상태

상태: 제안. 관련 요구사항: FR-07, FR-10.

### 배경

증거 수집, 원인 분석, 보고서 검토의 책임을 설명할 수 있어야 한다. 자유로운 다중 에이전트 대화는 행동 경로와 비용을 통제하기 어렵다. 처음부터 복잡한 Supervisor 계층을 여러 개 만드는 것은 과제 범위를 키운다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| 단일 도구 사용 에이전트 | 적은 호출, 단순한 기준 버전 | 조사와 검토의 역할을 분리하기 어려움 |
| 명시적 상태를 공유하는 역할별 그래프 | 흐름과 오류 위치가 보이고 검증하기 쉬움 | 상태 계약과 추가 호출 필요 |
| 자율 협상형 또는 계층형 Supervisor | 복잡한 조사에 유연함 | 예측 어려운 호출과 재계획 비용 |

### 선택안

LangGraph에서 하나의 조율 그래프가 Triage, Inspector, RCA, Reviewer를 실행한다. 각 역할은 별도 지시문, 입력·출력 스키마, 도구 권한을 가진다. Triage는 잠정 분류, Inspector는 제한된 MCP 도구 선택, RCA는 RAG와 원인 대조, Reviewer는 근거와 대응 검토를 담당한다.

고정된 기본 순서에 필요한 조건 분기만 둔다. Reviewer가 추가 증거를 요청하면 Inspector로 최대 1회 돌아가고, 표현·논리 수정은 RCA 재작성 최대 1회로 제한한다. 두 경로는 전체 호출 예산을 공유한다. 추가 LLM Supervisor를 별도로 두지 않고 조율은 그래프 코드가 담당한다.

일반 파싱·스키마 비교·통계는 도구 내부의 결정적 코드로 처리한다. 로그나 문서의 문장을 시스템 지시로 실행하지 않고 조사 자료로 사용한다. 공유 상태의 변경은 노드별 필드로 관리해 기존 증거를 덮어쓰지 않는다.

### 영향

역할별 테스트와 수행 기록이 가능하고 부적절한 추가 조사를 제한할 수 있다. 하나의 모델을 여러 역할에 사용해도 판단 오류가 독립적이라고 볼 수 없다. 호출 수 증가가 실제 품질 개선으로 이어지는지는 평가가 필요하다.

### 검증 조건

- 각 역할의 입력·출력·도구와 호출 기록이 구분된다.
- 증거가 부족한 경우에만 추가 조사를 수행하고 최대 횟수에서 종료한다.
- 잘못된 구조화 출력, 도구 실패, 예산 초과에서 상태가 누락되지 않는다.
- 역할이 같은 문서를 반복해서 읽거나 같은 조회를 불필요하게 수행하는지 개발셋으로 확인한다.

### 재검토 조건

단일 에이전트와 비교해 품질 이득이 없고 지연만 늘면 역할 통합을 검토한다. 새로운 장애 유형에 더 복잡한 계획이 필요하면 명시적 계획 노드를 추가한다.

공식 근거: [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api).

## ADR 0005 Qdrant 로컬과 BM25 Dense RRF 검색

상태: 제안. 관련 요구사항: FR-06.

### 배경

오류 코드·컬럼명은 정확한 키워드 검색이 유리하고 자연어 증상은 의미 검색이 유리할 수 있다. 문서 수는 작지만 검색 인터페이스와 근거 추적을 검증해야 한다. PDF의 FAISS 예시와 앞서 제안한 Qdrant를 동시에 구축할 이유는 없다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| BM25만 사용 | 빠르고 오류 키워드 확인이 쉬움 | 표현이 다른 증상 검색에 약할 수 있음 |
| FAISS와 별도 문서 저장 | 작은 로컬 검색에 적합 | 메타데이터와 저장 상태를 별도 관리 |
| Qdrant 로컬과 BM25 | 문서 메타데이터와 로컬 영속 저장을 같은 인터페이스로 관리 | 의존성·인덱스 구성과 임베딩 시간이 추가됨 |
| 원격 Milvus 또는 Qdrant 서버 | 다중 사용자와 확장 | 초기 운영과 서비스 연결 필요 |

### 선택안

qdrant-client의 디스크 기반 로컬 모드 하나를 사용한다. 별도 Qdrant 서버와 FAISS를 함께 띄우지 않는다. 로컬 저장소는 앱 프로세스 하나가 소유하며 동시 평가 프로세스가 같은 경로를 열지 않게 한다.

임베딩은 multilingual-e5-small, 키워드 검색은 별도 BM25 모듈을 사용한다. 입력 전처리, 청크, 문서 메타데이터는 두 검색기에서 동일하게 관리한다. query와 passage 접두사를 구분하고 모델 입력 한도를 검사한다.

초기 검색 정책은 각 검색기 상위 10개, RRF k=60, 문서 중복 제거 후 상위 3개다. 점수 척도가 다른 BM25와 Dense의 원점수는 직접 합산하지 않는다. 문서 내용, 모델 revision 또는 청킹 설정이 바뀌면 인덱스 버전을 갱신한다.

### 영향

키워드와 의미 검색을 결합하고 결과를 문서 버전까지 추적할 수 있다. 작은 데이터에서 하이브리드가 항상 더 정확하다는 보장은 없다. 첫 인덱스 구축·모델 다운로드 시간은 진단 지연과 분리해 기록해야 한다.

### 검증 조건

- 앱 재시작 후 저장한 문서와 벡터가 유지된다.
- BM25 단독, Dense 단독, RRF 결과를 개발셋에서 비교한다.
- Hit@3는 청크 3개가 아니라 서로 다른 문서 3개로 계산한다.
- 무관 문서·비슷한 증상의 다른 원인이 섞인 사례에서 검색 순위를 확인한다.
- 평가 정답, 장애 주입 라벨, 완성된 사례별 정답 보고서가 인덱스에 없다.

### 재검토 조건

동시 사용자나 큰 문서 집합이 필요하면 Qdrant 서버 모드로 이동한다. 하이브리드가 일관된 이득 없이 복잡성만 늘면 단일 검색 방식으로 변경하고 근거를 기록한다.

공식 근거: [Qdrant Client Local mode](https://github.com/qdrant/qdrant-client#local-mode), [Multilingual E5 Small](https://huggingface.co/intfloat/multilingual-e5-small).

## ADR 0006 실행에 연결된 증거와 구조화된 진단

상태: 채택(C의 실제 로컬 데모 범위, 2026-10-20). 실행·태스크·시도·invocation과 해시 검증, 현재/과거 구분을 적용했다. 연결 실패 시 run_results 미생성은 부분 명령 자료로 명시한다. 관련 요구사항: FR-04, FR-05, FR-08, FR-09.

### 배경

현재 DB 상태는 장애가 발생한 시점과 다를 수 있다. dbt의 target 파일은 이후 호출로 덮어쓰일 수 있다. 서로 다른 실행의 로그·산출물·스키마를 묶으면 그럴듯하지만 잘못된 원인 분석이 된다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| 최근 로그와 최신 target 파일을 읽기 | 간단한 구현 | 다른 실행·시도의 자료 혼입 |
| 모든 원시 데이터를 한 프롬프트에 넣기 | 수집 구조가 단순 | 출처·상한·시간 관계 검증이 어려움 |
| 식별자와 관측 시각을 가진 증거 묶음 | 주장과 원본을 연결하기 쉬움 | 산출물 저장과 자료 구조 관리 필요 |

### 선택안

증거는 dag_id, run_id, task_id, try_number와 연결하고 source, observed_at, evidence_id를 보관한다. 현재 DB 조회에는 관측 시각을 붙이고 과거 실행 당시의 스냅샷으로 가장하지 않는다. 정상 스키마 기준은 사전에 저장하고 baseline_id로 조회한다.

dbt_run과 dbt_test의 산출물은 서로 다른 경로에 저장한다. 실행·태스크·시도·호출별 manifest와 run_results를 쌍으로 보관하고 invocation 정보와 unique_id로 연결한다. 다음 명령이 같은 target을 덮어쓴 파일을 이전 태스크의 근거로 읽지 않는다.

manifest의 의존관계는 영향 가능성으로 표시한다. 실제 하위 실패는 실행 상태에서 확인한다. Diagnosis와 RecoveryAction을 Pydantic으로 검증하고 각 원인 주장에 존재하는 evidence_id를 연결한다. 충분한 근거가 없으면 UNKNOWN과 insufficient으로 반환한다.

### 영향

발표와 평가에서 어떤 증거로 판단했는지 추적할 수 있다. 스냅샷과 메타데이터 저장량이 늘고 현재 상태와 과거 상태를 다루는 코드가 필요하다. 근거 ID가 있다는 사실만으로 논리적 인과관계까지 입증되지는 않는다.

### 검증 조건

- 연속 두 실행과 같은 태스크의 재시도 산출물이 서로 덮어쓰이지 않는다.
- 다른 run_id 또는 invocation의 산출물을 섞은 경우 검출한다.
- 현재 스키마의 관측 시각과 정상 기준 시각이 보고서에 구분된다.
- 존재하지 않는 근거 ID, 대상 누락, 허용되지 않은 분류를 거부한다.
- 조회 연결이 성공해도 실패한 dbt 연결이 정상이라고 오판하지 않는다.

### 재검토 조건

동시 실행, 증거 보존 정책, 운영 데이터 접근이 추가되면 저장·보존·권한 정책을 확대한다. 실행 시점 스냅샷이 필수라면 수집 지점을 파이프라인 내부에 추가한다.

공식 근거: [dbt Manifest](https://docs.getdbt.com/reference/artifacts/manifest-json), [dbt Run results](https://docs.getdbt.com/reference/artifacts/run-results-json).

## ADR 0007 의미 검토와 코드 규칙 및 제한된 오류 복구

상태: 제안. 관련 요구사항: FR-09, FR-10, NFR-04, NFR-05, NFR-06.

### 배경

LLM이 제안한 명령이나 원인을 다시 LLM이 읽는 것만으로 실행 가능성과 정확성을 보장할 수 없다. 모든 오류를 재시도하면 잘못된 입력이나 스키마 문제에도 시간을 낭비한다. 한 도구의 실패를 정상 빈 값으로 처리하면 중요한 증거 누락을 숨긴다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| LLM 검토만 수행 | 의미적 설명 검토 가능 | 허용 대상·횟수·형식 같은 강제 조건 위반 가능 |
| 코드 규칙만 수행 | 명시한 조건을 결정적으로 검사 | 근거 해석과 조치 적절성을 충분히 평가하기 어려움 |
| 의미 검토와 코드 검사 결합 | 서로 다른 종류의 검사를 분담 | 추가 지연과 규칙 유지 필요 |

### 선택안

Reviewer는 관련성, 완전성, 근거 일치, 도메인 적절성을 검토한다. 별도 코드가 필수 필드, 대상과 근거 ID, 허용 조치, 상한을 강제한다. 파괴적 SQL, 임의 셸, 인증 정보 노출, 무조건적인 재시도는 허용하지 않는다. 검증된 명령 템플릿을 사용하는 경우도 첫 버전에서는 텍스트만 반환한다.

조회의 일시적 오류만 최초 시도 포함 최대 3회 재시도한다. 초기 대기는 0.5초와 1.5초로 하고 작은 지터를 적용하되 전체 마감 시각을 넘기지 않는다. 명시적 인증 거부, 잘못된 인자, 허용되지 않은 대상은 즉시 실패 처리한다. 잘못된 포트·스키마·품질 오류를 재시도로 해결된다고 설명하지 않는다.

도구별 10초, LLM 호출별 30초, 진단 전체 180초를 상한으로 둔다. LLM 6회, MCP 10회, 검색 2회에 모든 재시도를 포함한다. 추가 조사와 재작성은 각각 1회 이내이며 먼저 소진되는 제한에서 종료한다.

부분 실패 시 확보한 사실과 누락을 보고한다. 원인에 필수인 증거가 없으면 원인 확정과 복구 권고를 보류한다. Reviewer 통과와 실제 복구 완료는 별도 필드로 저장한다.

### 영향

무한 반복과 일부 부적절한 조치를 제한할 수 있다. 중단 때문에 답변을 완성하지 못할 수 있고 규칙이 너무 엄격하면 유효한 조치도 보류될 수 있다. 검토 결과는 운영 안전성 인증이 아니다.

### 검증 조건

- 타임아웃, 반복 1회 초과, 호출 예산 초과에서 정해진 상태로 종료한다.
- 잘못된 인자와 인증 실패를 반복 호출하지 않는다.
- 스키마 오류에 재시도만 제안한 결과와 존재하지 않는 대상·근거 ID를 차단한다.
- 로그만 성공하고 DB 조회가 실패한 경우 누락 사실과 제한된 결론을 표시한다.
- 검토 통과 전후에 DB·DAG의 상태를 변경하지 않는다.

### 재검토 조건

운영 환경에서 작업별 정상 지연이 달라지면 상한을 실측 근거로 조정한다. 자동 실행을 추가하면 멱등성, 승인, 대상 재확인, 실행 후 검증을 새 설계로 다룬다.

## ADR 0008 Streamlit과 명시적 진단 실행

상태: 제안. 관련 요구사항: FR-11, FR-12, NFR-07.

### 배경

PDF에는 FastAPI, React, SSE가 포함돼 있지만 과제의 핵심은 장애 진단 기능이다. 1인 로컬 데모에서 별도 프런트엔드와 전송 프로토콜을 구현하면 시간과 동작 지점이 늘어난다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| CLI만 제공 | 빠르고 자동화에 편리 | 평가자가 근거와 상태를 한눈에 보기 어려움 |
| Streamlit | 입력·표·로그·내보내기를 빠르게 구성 | 재실행 모델과 연결 수명 관리에 주의 필요 |
| FastAPI와 React 및 SSE | 백엔드 분리와 단계별 스트리밍에 적합 | API, 프런트 상태, 이벤트 형식, 연결 관리 구현 필요 |

### 선택안

Streamlit 한 화면에서 실행 선택, 진단 버튼, 상태, 근거, 검색 문서, 조치, 후속 실행 결과, JSON 내보내기를 제공한다. 결과는 세션 상태에 저장하고 화면 갱신만으로 진단을 다시 실행하지 않는다.

비동기 MCP 세션은 앱 실행 계층이 하나의 일관된 이벤트 루프와 명시적 연결 컨텍스트에서 관리한다. Streamlit 재실행 사이에 종료된 루프에 연결된 객체를 그대로 보관하지 않는다. 단일 앱 프로세스에서 동시에 활성화되는 진단은 하나로 제한한다.

### 영향

핵심 결과를 빨리 시연할 수 있고 별도 API 운영을 줄인다. 다중 사용자나 API 소비자 지원은 목표에서 빠진다. 연결 수명과 세션 상태를 검사하지 않으면 중복 실행이나 이벤트 루프 오류가 발생할 수 있다.

### 검증 조건

- 결과 화면을 새로고침해도 LLM·MCP 호출이 자동으로 증가하지 않는다.
- 두 진단을 순차 실행하고 앱 종료 시 프로세스·세션이 정리된다.
- 사용자가 실제 근거와 누락을 펼쳐 보고 JSON 결과를 저장할 수 있다.
- 후속 실행의 성공을 원래 장애 실행의 성공으로 덮어쓰지 않는다.

### 재검토 조건

다중 사용자, 외부 API, 장기 작업, 세밀한 진행 이벤트가 필요하면 FastAPI와 SSE로 분리한다. 이때 자원 수명은 lifespan에서 관리하고 UI 이벤트 스키마를 별도 정의한다.

공식 참고: [FastAPI Lifespan](https://fastapi.tiangolo.com/advanced/events/). FastAPI는 첫 버전의 필수 의존성으로 추가하지 않는다.

## ADR 0009 고정 증거 기반 비교와 실제 통합 검증 분리

상태: 제안. 관련 요구사항: FR-13.

### 배경

평가마다 실시간 상태가 바뀌면 입력이 달라져 개선 효과를 비교하기 어렵다. Faithfulness가 높더라도 실제 원인을 맞혔다는 의미는 아니다. 한편 모든 평가를 fixture로만 수행하면 실제 MCP 연동을 확인하지 못한다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| 실행마다 실제 시스템을 새로 조회 | 최신 상태를 사용 | 상태 변동과 재현 비용 때문에 비교가 불안정 |
| LLM Judge 점수만 사용 | 평가 자동화가 쉬움 | 원인 정답과 실행 가능성 검증 부족 |
| 고정 증거 평가와 실제 E2E 분리 | 같은 입력의 비교와 실제 연동을 각각 확인 | 두 평가 경로와 결과 구분 필요 |

### 선택안

실제 도구 조회는 IT와 세 장애의 E2E로 확인한다. 품질 비교는 고정된 EvidenceBundle을 같은 스키마의 재생용 추출기로 제공한다. 기본 버전과 최종 버전은 같은 상태·로그·스키마·통계를 받는다. 최종 버전만 검색 문서와 역할별 검토를 추가한다.

개발셋 6건과 최종셋 12건을 분리한다. 최종셋은 장애 9건, 정상 1건, 근거 부족 2건이다. 정답, 허용 문서 ID, 금지 조치, 채점 기준은 에이전트에 전달하지 않는다. 평가 전에 모델, 프롬프트, 문서·인덱스, 코드 버전과 증거 해시를 고정한다.

원인 채점은 유형뿐 아니라 사례별 원인 요소와 필수 근거를 함께 검사한다. 문장 전체의 정확 일치나 키워드 유무만으로 정답을 만들지 않는다. 모호한 결과는 정해진 채점표에 따라 사람이 확인하고 근거를 남긴다. LLM Judge는 보조 평가로 사용한다.

PDR의 8/9 진단, 8/9 검색 적중, 정상·보류 3/3, E2E 3/3은 목표다. 여러 기능을 묶어 비교한 결과를 Multi-Agent 하나의 효과라고 주장하지 않는다.

### 영향

재현 가능한 비교와 실제 동작 확인을 함께 제공한다. 작은 합성 사례의 점수는 분산이 크고 실제 운영 일반화를 보장하지 않는다. 최종 평가를 보고 프롬프트를 바꾸면 이전 결과와 구분해 새 실험으로 표시해야 한다.

### 검증 조건

- 기준·최종 버전 입력의 증거 해시가 같고 정답 필드가 없다.
- 실행별 실패·시간 초과·미수집 사용량도 결과에 포함한다.
- 지표의 분모 9와 3 및 실제 시연 3을 섞지 않는다.
- NEG의 근거 조작·대상 누락·재시도 오용·로그 누락·연결 오판·과거 산출물 혼입을 검사한다.
- 평가 보고서에 시스템 전체 비교라는 해석과 합성 데이터 한계를 명시한다.

### 재검토 조건

기능별 인과 효과가 필요하면 동일한 검색·증거를 유지한 제거 실험을 추가한다. 실제 장애 기록이 확보되면 익명화와 분리 원칙을 정해 평가셋을 확대한다.

공식 근거: [LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation), [Ragas Faithfulness](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/faithfulness/).

## ADR 0010 로컬 추적과 의존성 주입 및 선택적 외부 관측

상태: 제안. 관련 요구사항: NFR-08, NFR-09, FR-10.

### 배경

어느 도구와 모델이 어떤 입력을 받았는지 기록이 없으면 잘못된 원인을 재현하기 어렵다. 관측 도구 연결 자체가 개발의 전제가 되면 외부 계정과 서비스 문제로 핵심 진단이 막힐 수 있다. 전역 클라이언트를 직접 참조하면 테스트에서 실패 조건을 만들기 어렵다.

### 비교 대안

| 대안 | 이점 | 부담과 한계 |
| --- | --- | --- |
| print 로그와 전역 클라이언트 | 적은 초기 코드 | 진단별 추적·재현·테스트 교체가 어려움 |
| 로컬 구조화 기록과 의존성 주입 | 외부 서비스 없이 테스트와 비교 가능 | 기록·버전·교체 인터페이스 구현 필요 |
| LangSmith와 전체 관측 스택을 필수 구성 | 풍부한 추적과 대시보드 | 계정·네트워크·추가 서비스 의존 |

### 선택안

모든 진단에 incident_id와 trace_id를 부여한다. 로컬 JSON 기록에 실행 식별자, 노드, 도구, 관측 상태, 시간, 모델과 프롬프트 버전, 인덱스 버전, 사용량을 남긴다. 진단 입력의 증거 묶음과 결과는 해시로 연결한다. 키와 비밀번호는 기록하지 않는다.

Extractor, Retriever, LLMClient, TraceSink를 생성 단계에서 주입한다. 실제 연결과 replay 또는 mock 구현이 같은 계약을 사용하게 한다. 단위 테스트는 외부 API를 호출하지 않고 실제 연결은 IT에서 확인한다. 현재 State와 결과 저장을 구현하되 대화 Checkpointer의 영속 저장은 첫 버전 필수에서 제외한다.

LangSmith는 선택적 TraceSink로 연결한다. 꺼져 있거나 전송이 실패해도 로컬 기록과 핵심 진단을 유지한다. 연결하면 에이전트·도구 실행과 실험을 확인하되 원문 로그를 외부로 보내는 범위는 합성 데이터로 제한한다.

Prometheus·Grafana·Loki·Tempo는 파이프라인과 분산 서비스 관측의 후속 범위로 둔다. LangSmith의 에이전트 추적과 역할이 다르므로 서로 대체한다고 설명하지 않는다.

### 영향

실패 재현, 비용·지연 비교, 테스트 교체가 쉬워진다. 로컬 파일은 다중 프로세스 동시 쓰기와 검색에 한계가 있고 외부 추적을 쓰면 전송과 보존 정책이 추가된다. 제공자가 토큰을 반환하지 않을 경우 사용량이 미수집일 수 있다.

### 검증 조건

- 외부 추적을 꺼도 전체 진단과 평가가 동작한다.
- 하나의 진단에서 증거·노드·최종 결과를 같은 식별자로 따라갈 수 있다.
- mock LLM과 추출기를 주입해 타임아웃·부분 실패를 재현한다.
- 제공자 미수집 토큰을 0으로 저장하지 않고 비용 추정의 단가·기준일을 남긴다.
- 로그에 비밀값이 없고 진단 종료 후 결과가 로컬 파일로 남는다.

### 재검토 조건

다중 사용자·인스턴스, 긴 대화, 재시작 후 작업 재개가 필요하면 PostgreSQL Checkpointer를 검토한다. 외부 관측과 자동 경보가 필수인 운영 단계에서는 수집·보존·접근 정책을 별도 ADR로 정한다.

공식 근거: [LangSmith Evaluation](https://docs.langchain.com/langsmith/evaluation), [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api).

개념 자료: AI캠퍼스_AI_Capstone_20261016.pdf의 PDF 뷰어 기준 7~10쪽 ADR, 39~69쪽 MCP, 123~171쪽 에이전트·검토, 175~178쪽 오류 처리, 217~222쪽 모듈·테스트, 238~251쪽 관측·평가. 자료의 비교 대안과 예시 구현은 본 프로젝트의 필수 요건과 구분한다. 원본 PDF는 이 배포에 포함하지 않는다.


## C-0011 실제 Linux 개발 컨테이너와 실행별 부분 산출물

상태: 채택, 2026-10-20. C 사본에만 적용하며 원본 ADR은 변경하지 않는다.

macOS의 Airflow 2.10.4 webserver·scheduler 로그 서버 작업자가 SIGSEGV로 종료됐다. 해당 프로세스를 중지한 뒤 같은 버전의 공식 Linux 이미지에서 webserver와 scheduler를 SQLite·SequentialExecutor 개발 구성으로 실행했다. dbt Core 1.9.10와 postgres 1.9.1, 드라이버를 각자 별도 가상환경으로 분리했다. 업무 DB는 PostgreSQL 17.10 전용 컨테이너다. 호스트 포트는 18783과 15439로 loopback에만 공개한다.

실제 연결 실패에서 manifest는 생성됐지만 run_results는 생성되지 않았다. 없는 파일을 합성하지 않고 partial 자료로 보존하며, 실제 명령 로그·manifest invocation과 해시가 검증된 경우에만 선택 실행의 연결 거부 로그와 함께 사용한다. 스키마·품질·정상 판정은 완전한 결과를 요구한다.

검증: `uv run python scripts/live_e2e.py` 종료 0, 정상 1회·장애 3회·후속 3회, 실제 복구 3/3. 모든 후속 run에서 태스크 4개, not_null·unique, 1,000건·502,360.39 집계를 확인했다. 실제 stdio MCP가 Airflow API·PostgreSQL·dbt 보관 파일에 도달했다. DB INSERT·UPDATE·CREATE는 42501, Viewer의 실행 요청은 403이었다. `live_limits.py`와 `live_post_recovery.py`도 종료 0이다. 증거는 `artifacts/checkpoint2/`에 있다.

ADR-0003의 실제 프로토콜·연결 조건은 통과했지만 MCP Inspector UI와 LangChain MCP adapter는 사용하지 않아 원래 ADR 전체의 채택으로 표시하지 않았다. ADR-0004·0005·0007·0008·0009·0010은 실제 LLM·추가 조사·하이브리드 검색·화면·평가 또는 추가 관측 계약이 남아 제안을 유지한다.

재검토: 운영 배포나 다중 사용자, 실제 LLM 연결, SQLite를 넘는 실행 구성이 필요하면 이 개발 전용 결정을 새 ADR로 대체한다.

## C-0012 공유 키의 명시적 저비용 LLM 연결

상태: 제한된 로컬 데모 범위 채택, 2026-10-20. C 사본에만 적용한다.

사용자가 제공한 공유 API 키는 명시적인 로컬 파일에서만 읽고 600 권한을 적용한다. 런타임·캐시는 700, 장부·캐시는 600이다. 네 역할 모두 `gpt-6-luna`, reasoning none, 기본 service tier, store=false, 유료 호스팅 도구 없음으로 제한한다. 응답은 strict JSON Schema와 코드 검토를 함께 통과해야 한다. 근거 ID와 런북 문서 ID는 서로 다른 동적 enum으로 제한한다. Reviewer는 같은 모델의 별도 호출이다.

SQLite 선예약으로 하루 $0.02·누적 $0.05·진단 $0.01·진단 4요청을 검사하고 자동 API 재시도·모델 전환·유료 RCA 재작성은 금지한다. 성공한 역할은 24시간 로컬 캐시를 사용한다. 미확인 사용량은 예약액을 유지하고, 예약을 넘는 실제 사용량이면 추가 호출을 차단한다. API 응답 토큰과 2026-10-20 단가를 적용한 추정치이며 공용 계정 전체 결제 한도가 아니다.

검증: 전체 pytest 71개, 실제 API 요청 7회·누적 추정 $0.00264445. 저장된 실제 스키마 장애 증거의 진단·검토 통과, 동일 재실행 API 0회·캐시 4회. 초기 출력 잘림과 잘못된 ID의 거절도 보존했다. 실키 출력물 노출은 0개, 서비스는 중지 상태다. 상세 명령·결과는 상위 `CHECKPOINT_3.md`와 `artifacts/checkpoint3/`에 있다.

재검토: 단가 변경·모델 변경·여러 앱의 공용 사용·실제 운영 데이터·다중 사용자·전체 평가 확장 시 비용·키 저장·보존 정책을 다시 검토한다. 원래 ADR-0004·0005·0007·0008·0009·0010의 미완료 조건은 이 결정으로 면제하지 않는다.

## C-0013 로컬 하이브리드 검색·화면·고정 평가 재료

상태: 구현·제한된 검증 완료, 성능 목표는 미달. 2026-10-20, C 사본에만 적용한다.

직접 작성한 런북 9개·별도 합성 이력 3개에 공식 multilingual-e5-small qint8 ONNX·CPU와 Qdrant 디스크 모드, BM25·RRF k=60을 적용한다. 원래 모델 revision·prefix·pooling·L2·토큰 경계와 문서별 top3를 검사한다. qint8과 float 원본의 동등성은 미검증이다. LLM에는 직접 작성한 압축 절차 요약을 보내며 원문·대표 청크를 보존한다. 추가 유료 임베딩·요약은 없다.

Streamlit은 저장 결과를 기본으로 명시적인 form만 새 진단을 시작한다. 루프·MCP 컨텍스트는 실행마다 소유하고 결과 JSON만 세션에 둔다. 실제 브라우저에서 열람·탭·선택·내보내기·새로고침은 추가 API 0회였고, 무료 모델 대역을 사용한 실제 MCP form 진단도 확인했다. paid 버튼 경로를 브라우저에서 유료로 다시 시험하지는 않았다.

개발 6·최종 12, 별도 정답과 평가 전 동결을 사용했다. 최종 양쪽은 같은 Evidence 해시이며 기준에 검색 본문을 주지 않는다. 검색 9/9, 원문 대조 Codex 원인 판정은 양쪽 5/9로 정확도 우위를 입증하지 못했다. 최종 결과를 보고 prompt를 조정해 점수를 높이지 않았다. 원래 성능·사람 검토·운영 조건은 충족했다고 표시하지 않는다.

## C-0014 같은 금액 한도 아래 Flex 평가와 컨테이너 키 격리
