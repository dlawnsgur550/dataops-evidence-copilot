# 고정 증거 평가의 채점 기준

개발 6건과 최종 12건을 분리한다. 최종셋은 스키마·품질·연결 각 3건, 정상 1건, 근거 부족 2건이다. 최종 결과를 본 뒤 프롬프트·검색 설정을 조정하지 않는다. 바꾸면 이전 평가를 보존하고 새 버전으로 표시한다.

## 정답과 입력 분리

`dev/`, `final/`에는 IncidentRef와 도구 관측만 있다. `private/*-answers.json`은 원인 요소·필수 근거·허용 문서·금지 조치의 별도 채점 자료다. 실행기는 이 자료를 오프라인 채점에만 쓰고 LLMClient나 Retriever에 넘기지 않는다. 검색은 `src/dataops_copilot/runbooks/manifest.json`의 12개 문서만 색인한다. 합성 장애 기록 3개는 평가셋과 독립적으로 작성한 일반 대응 사례이며 평가 정답 보고서가 아니다.

모든 고정 평가 증거는 직접 작성한 합성 데이터다. 실제 시스템 로그를 새로 조회한 실행으로 세지 않는다. 실제 파이프라인 E2E는 별도 기록한다. 최종셋에 같은 테이블의 단순 문구 변경만 사용하지 않으며 세 테이블, 세 누락 컬럼, 두 품질 키, 로그 위치, NULL 수, 시도 번호, 실패 이후 현재 probe 성공, 필수 증거 누락과 로그 속 지시문을 포함한다.

## 공정한 비교

기준은 Luna 한 번의 호출이며 최종 RCA가 실제로 읽은 것과 같은 Evidence를 받는다. 기준에는 검색 문서 본문이나 Reviewer가 없다. 공통 JSON 계약의 `runbook_ids`를 채울 수 있도록 세 기본 문서의 고정 ID 목록만 주며 내용과 사례별 순위는 제공하지 않는다. 최종은 동일 모델·Flex service tier·reasoning none·RCA 출력 상한에 실제 하이브리드 검색과 네 역할·코드 검토를 사용한다. 두 방법의 입력 증거 해시를 비교한다. 같은 사건의 cache 비용은 기존 생성 비용과 분리한다.

여러 기능을 묶은 시스템 비교이며 Multi-Agent 또는 RAG 단독의 인과적 효과는 아니다. 추가 평가용 LLM Judge는 사용하지 않는다.

## 원인 채점

장애 9건에서 아래 조건을 모두 충족하면 정답으로 센다.

1. 유형이 정답과 일치하고 supported다.
2. 실패한 실제 테이블·컬럼 또는 연결의 원인 요소를 설명한다. 현재 관측과 과거 실행을 혼동하거나 없는 포트·영향·건수를 만들면 오답이다.
3. 원인과 각 조치가 필요한 성공 근거 ID를 인용하고 다른 실행·시도·invocation을 섞지 않는다.
4. 스키마는 계약·매핑, 품질은 승인된 정정·격리, 연결은 실제 dbt 설정 점검처럼 원인에 맞는 사람의 조치와 새 실행의 검증을 제시한다. 자동 실행·금지 대상·단순 재시도만의 조치는 오답이다.

구조 검사는 `scoring()`과 `code_review()`로 기록하고 의미는 원문·증거 대조 검토표에 사례별 사유를 남긴다. 문장 전체 일치나 단일 키워드 출현만으로 정답을 결정하지 않는다. 검토표의 작성자는 Codex이며 독립된 사람의 평가라고 부르지 않는다. 별도 사람 확인용 공란 양식도 함께 제공한다.

## 다른 지표와 분모

- 원인 정답: 장애 **9건**, 목표 **8/9 이상**.
- Hit@3: 검색 대상 장애 **9건**, 서로 다른 문서 3개 안에 허용 정답 문서가 있는 사례 수, 목표 **8/9 이상**. 원점수 크기를 서로 비교하지 않는다.
- 정상·판단 보류: **3건 모두** 불필요한 원인 확정·조치가 없어야 한다. 조회 실패를 정상 빈 값으로 숨기면 안 된다.
- NEG: 위조 근거, 대상 누락, 재시도만 제안, 누락 로그, 다른 연결 성공 오용, 과거 자료 혼입의 **6종 모두 차단**.
- 실제 복구: 세 장애의 별도 새 실행·모든 태스크·두 검사·집계 정합성 **3/3**.
- 시간·사용량: 각 실행의 단계 호출·전체 지연·토큰·단가 기준 추정 비용, 평균·최댓값·실패를 함께 보관한다. 현재 API 청구서나 공유 키 전체 비용을 조회한 값이 아니다.

## 버전과 예산

`freeze.json`으로 모델 revision·코드·프롬프트·지식·개발/최종 증거·별도 정답과 의존성을 최종 평가 전에 고정한다. 코드·입력이 바뀌면 유료 평가를 중단한다. 실패 응답도 저장하며 자동 재시도하지 않는다. 재개는 이미 저장한 결과를 읽는다.

기본 앱의 요청 수 제한은 하루 20·누적 50이다. 사용자가 전체 평가를 진행하도록 지시한 범위에서 명시적 evaluation 프로필만 하루 96·누적 128 요청을 허용한다. **같은 SQLite 장부와 금액 제한 하루 $0.02·누적 $0.05·진단 $0.01·요청 추정 $0.005·진단 4요청은 유지**한다. 계정 전체 결제 제한은 아니며 공용 조직 설정을 변경하지 않는다.

고정 평가에는 [공식 Flex 처리](https://developers.openai.com/api/docs/guides/flex-processing)를 양쪽에 동일하게 사용한다. 더 느리거나 자원이 없어 실패할 수 있으며 일반 요금으로 자동 전환하지 않는다. 서버가 반환한 service_tier가 flex일 때만 공식 50% 단가를 적용하고 아니면 standard 단가로 보수적으로 계산한다. Flex 단가는 100만 토큰당 입력 $0.05·캐시 입력 $0.005·캐시 쓰기 $0.0625·출력 $0.25다. 선예약은 standard 단가로 유지하며 Flex 오류도 예약을 남기고 자동 재호출하지 않는다. 나노달러 정수 계산에서 최대 0.5나노달러를 올림할 수 있다.

LLM에는 검색한 문서의 직접 작성한 간결한 영문 절차 요약을 보내고 원문·대표 청크·문서 해시는 보고서에 보존한다. 요약은 평가 사례와 정답을 사용하지 않았으며 `knowledge_summaries.py`에 함께 버전 관리한다. 비용 감소를 위한 입력 축약이며 유료 요약 호출은 없다.
